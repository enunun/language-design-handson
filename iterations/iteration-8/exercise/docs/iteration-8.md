# Iteration 8 組

このIterationでは，Miniに組`(t, u)`，射影`fst t`と`snd t`，組の型`A × B`を足す．
これまでと違い，評価と型付けの推論規則は自分で設計する．
設計した規則のもとで，これまでの性質がすべて成り立つことを証明する．

## 8-1 準備

このパッケージは，Iteration 7の解答と同じ状態から始まる．

``` sh
cd iterations/iteration-8/exercise
lake build
lake test
```

Iteration 7までのテストがすべて通ることを確かめる．
`handout/Parser.lean`は，組と射影と組の型に対応した構文解析器である．
組の型の`×`は`*`とも書ける．

## 8-2 構文と概念

次の2つのノートを読む．

- [再帰的な値についての帰納法](../../../docs/lean/iteration-8.md)
- [推論規則を設計する](../../../docs/semantics/iteration-8.md)

読み終えたら，`Scratch.lean`で次の課題を試す．

1. ノートの`sum_mirror`について，`cases`を使う証明と`induction`を使う証明を比べる．
2. 組を先行評価する場合と遅延評価する場合で，$\mathsf{fst}\ (1 + 2, \mathsf{iszero}\ 0)$を紙の上で簡約する．それぞれ何ステップで値になるか．
3. 組を先行評価する場合と遅延評価する場合で，`Value`の定義はどう変わるか．

## 8-3 テストリスト

### 要件

- 組`(t, u)`，射影`fst t`と`snd t`，型`A × B`を足す．
- 評価と型付けの推論規則は，自分で設計する．

### 使用例

```text
$ lake exe mini check "fun (p : Nat × Bool) => if snd p then fst p else 0"
Nat × Bool → Nat
$ lake exe mini eval "fst (1 + 2, true)"
3
```

### 作るもの

| モジュール | 定義 | 内容 |
| --- | --- | --- |
| `Mini.Syntax` | `Ty`の構成子`prod (A B : Ty)` | 組の型 |
| | `Term`の構成子`pair (t u : Term)`，`fst (t : Term)`，`snd (t : Term)` | 組と射影 |
| | `Value`の構成子 | 組の値．何を持つかは設計で決める |
| `Mini.Typing` | `TypeError`の構成子`notPair (actual : Ty)` | 組でない式の射影 |
| そのほか | 各モジュールに組と射影の場合を足す | 推論規則の構成子の名前も自分で決める |

組でない式を射影したときの型エラーは，`組でない式から成分を取り出している(型：Nat)`の形にする．
組は`(1, true)`の形で，組の型は`Nat × Bool`の形で表示する．
`×`は`→`より強く結合し，右に結合する．

### 課題

まず，次のことを決める．

- 組の成分を，いつ評価するか．組はいつ値になるか．
- 成分を評価するなら，どの順序で評価するか．
- 射影は，組がどうなったときに成分を取り出すか．

決めたことに沿って，確かめるべきことを`TESTLIST.md`に書き出す．

- 組と射影の評価，簡約，型付けの具体例を考える．設計の選択が現れる例を入れる．
- 型エラーの具体例を考える．
- 既存の定理のうち，組の場合を足す必要があるものを挙げる．証明の方法が変わるものはあるか．

## 8-4 設計書

- `design/spec.md`
  - `## 構文`，`## 値`，`### 値を表す式\`IsValue\``，`### 置換`に，組と射影を足す．
  - 大ステップ意味論と小ステップ意味論に，自分で設計した規則を足す．組の成分をいつ評価するかの判断と，その理由を書く．
  - `## 型`に組の型と，組と射影の型付け規則を足す．
- `design/modules.md`：依存の矢印は変わるか．

規則は，実装より先に設計書へ書く．
規則を書いたら，次のことを紙の上で確かめる．

- 同じ式に当てはまる小ステップ意味論の規則が，2つ以上ないか．
- 型の付く閉じた式が，値であるか，どれかの規則で簡約できるか．
- 大ステップ意味論と小ステップ意味論が，同じ値を与えるか．

## 8-5 テストファーストの実装

### 構文と構文解析器

1. `Ty`，`Term`，`Value`に構成子を足し，構文解析器を置き換える．
2. `lake build`で，場合が足りない定義と証明の一覧を確かめる．

### 意味論と評価器

テストリストの順に具体例を足し，`subst`，`Eval`，`IsValue`，`Step`，`step`，`Term.toValue?`，`Value.toTerm`に場合を足す．
既存の定理の証明にも，組と射影の場合を足す．

次のヒントを参考にする．

- `Value`が組を持つと，`Value.toTerm`と`Term.toValue?`は再帰的な関数になる．
- 値についての補題(`value_normal`，`isValue_toTerm`，`toValue?_toTerm`など)は，`cases`を`induction`に変える．
- `step_complete`の値を表す式についての場合は，`isValue_exists_value`で式を`v.toTerm`の形にしてから，`toValue?_toTerm`で`step`を計算する．

### 型付け

`HasType`と`typeOf`に組と射影の場合を足し，`TypingTest`の定理を広げる．

次のヒントを参考にする．

- 進行の射影の場合には，組の型を持つ値は組であるという標準形補題が要る．
- 保存の射影の場合は，組の型付けを`cases`で分解して成分の型付けを取り出す．

### 表示と`run`

`Term.pretty`，`Value.pretty`，`Ty.pretty`，型エラーの表示を直し，統合テストを足す．

最後に，使用例のとおりに表示されることを確かめる．

## 8-6 振り返り

1. 自分の`TESTLIST.md`を，`solution/TESTLIST.md`と比べる．
2. 自分の設計と模範解答の設計を比べる．違う選択をした場合，証明が難しくなった定理と易しくなった定理はどれか．
3. 小ステップ意味論で，右の成分を簡約する規則から「左の成分が値である」前提を落とすと，どの定理の証明が通らなくなるか．
4. 設計書と実装を見比べ，`mise run check-design`で`一致`になるまで設計書を直す．

## 8-7 発展課題

自分が選ばなかった設計の簡約を，テストファイルの中で定義する．
2つの設計で振る舞いが変わる式の例を見つけて，そのことを証明する．
その式に型は付くか．

これも，テストリスト，設計書，実装の順に進める．
